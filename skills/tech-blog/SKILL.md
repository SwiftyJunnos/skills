# 테크 블로그

독자가 문제의 맥락을 이해하고, 원리를 익히고, 자기 상황에 적용할 수 있는 기술 글을 완성한다. 기본 흐름은 **배경 → 개념 → 활용 → 회고**다. 사용자가 다른 구성이나 매체를 지정하면 그 요청을 따른다.

## 자료와 논지

- 대화, 코드, 실험 결과, 이슈·PR, 기존 글에서 문제와 근거를 수집한다. 이전 세션을 참고하라는 요청에는 관련 대화의 사용자 요청과 수정 피드백도 확인한다.
- 독자와 핵심 질문을 정한다. 별도 지정이 없으면 해당 프로젝트의 내부 사정을 모르는 개발자를 기준으로, 요청 언어로 쓴다. 글의 방향을 정할 수 있으면 바로 작성한다.
- 관측한 사실, 원인에 대한 해석, 아직 검증하지 않은 가설을 구분한다. 수치와 경험담은 자료가 뒷받침하는 범위에서만 쓴다. 근거가 부족하면 설명 범위를 좁히거나 미확인 사항을 명시한다.
- 제목은 구체적인 현상이나 독자가 얻을 이해를 드러낸다. 목차를 제시하는 데서 멈추지 않고 본문과 필요한 시각 자료까지 만든다.

## 글의 흐름

네 단계는 설명 순서다. 소제목은 내용에 맞게 붙이고 분량도 논지에 따라 배분한다. 기존 글을 고칠 때도 이 연결이 이어지는지 확인한다.

### 배경

실제로 무엇이 불편했는지, 왜 해결하거나 이해해야 했는지부터 시작한다. 구체적인 증상, 기존 방식, 제약과 목표를 제시한다. 프로젝트 이름이나 이슈 번호를 몰라도 문제를 이해할 수 있어야 한다.

### 개념

활용 사례를 읽는 데 필요한 원리를 먼저 설명한다. 용어를 처음 사용할 때 역할과 경계를 풀어 쓰고, 각 구성 요소가 무엇을 맡고 누가 실행을 시작하는지 연결한다. 프레임워크, 웹 서버, 작업 큐, 프로세스처럼 혼동하기 쉬운 계층은 구분해서 보여 준다.

비유를 쓰면 실제 동작으로 이어 간다. 여러 대안이 논지에 중요하면 같은 기준으로 비교하고, 선택에 영향을 준 차이를 설명한다. 비교표 뒤에는 그 차이가 이번 문제에 갖는 의미를 문장으로 풀어 쓴다.

### 활용

개념을 실제 문제에 적용한다. 문제를 좁힌 근거, 선택한 방식과 이유, 핵심 구현이나 설정, 검증 결과가 이어지게 쓴다. 필요한 코드만 보여 주고 코드 앞뒤에서 왜 필요한지와 무엇이 달라지는지 설명한다.

결과에는 적용 조건과 비용을 함께 적는다. 성능 글이라면 환경, 측정 구간, cold/warm 구분을 밝히고 시작 시간과 전체 처리 시간을 구별한다. 측정하지 않은 전체 성능을 부분 측정에서 추정해 성과로 제시하지 않는다. 개념 중심 글은 구체적인 사용 예와 적용하기 어려운 조건으로 이 단계를 구성한다.

### 회고

어떤 가정이 맞거나 틀렸는지, 무엇을 얻고 어떤 비용을 감수했는지 돌아본다. 다음에 같은 문제를 만나면 바꿀 판단이나 확인 절차를 구체적으로 남긴다. 남은 한계와 미검증 항목도 포함한다. 자료에 없는 실패담이나 감정을 만들어 넣지 않는다.

## 시각화는 본문의 일부

**의미 있는 수치 비교와 구조·실행 흐름 설명에는 시각화를 기본으로 포함한다.** 독자가 머릿속에서 관계나 크기를 재구성해야 하는 대목마다 차트나 도식으로 읽는 부담을 줄인다. 장식용 대표 이미지로 설명용 시각화를 대신하지 않는다.

- 수치의 변화·분포·비교는 차트로, 구성 요소의 관계는 구조도로, 처리 순서와 주체는 흐름도·시퀀스도로 보여 준다. 전후 구조가 달라졌다면 같은 범례로 나란히 비교한다.
- 그림 내부에는 시각화한 정보와 이를 읽는 데 필요한 최소한의 레이블·수치만 간결하게 담는다. 배경, 해석, 주의사항, 출처 등 부가 설명은 본문에 둔다.
- 그림은 관련 문단 가까이에 배치한다. 무엇을 보여 주는지 짧은 캡션을 붙이고, 본문에서 독자가 읽어야 할 차이와 의미를 해석한다.
- 시각 자료가 필요한 글에서는 [시각화 제작·검증 기준](references/visuals.md)을 읽고 실제 자료를 제작한다. 그림 자리표시자나 제작 제안만으로 완료하지 않는다.
- 단일 수치나 자명한 한 단계처럼 그림의 이득이 거의 없을 때는 문장이나 작은 표로 충분하다. 사용자의 텍스트 전용 요청도 따른다. 자료나 도구가 부족하면 수치·관계를 꾸미지 말고 가능한 도식과 남은 한계를 밝힌다.

## 문체와 전달

- 연결된 문단으로 설명한다. 목록은 절차·조건·비교를 읽기 쉽게 할 때 사용하고, 변경 파일이나 명령 나열이 글 전체를 대신하지 않게 한다.
- 낯선 용어와 약어를 풀어 쓰되 필요한 기술적 깊이는 유지한다. 결론과 이유를 분명히 쓰고, 막연한 효과·과장·상투적인 교훈을 구체적인 동작과 근거로 바꾼다.
- 처음 읽는 사람에게 필요한 코드·문서 출처를 해당 주장 가까이에 연결한다. 버전에 따라 달라지는 외부 동작은 해당 버전의 공식 자료로 확인한다. 내부 주소와 식별자는 독자와 공개 범위에 맞게 처리한다.
- 사용자가 지정한 파일·위키·블로그 형식으로 전달한다. 게시를 요청받았다면 본문과 이미지를 함께 전달하고 발행본을 다시 읽어 확인한다. 로컬 초안 완성과 게시 성공을 구분하며, 이 스킬의 선택만으로 외부 게시 권한을 얻었다고 해석하지 않는다.

## 완료 확인

독자가 다음 질문에 답할 수 있는지 읽어 본다.

- 왜 이 문제가 생겼고 해결할 가치가 있었나?
- 어떤 원리로 동작하며 각 구성 요소는 무슨 역할인가?
- 어떻게 적용했고 무엇을 확인했으며 어떤 조건에서 유효한가?
- 무엇을 배웠고 어떤 비용·한계가 남았나?

마지막으로 본문·코드·그림의 수치와 용어가 일치하는지, 설명에 필요한 시각화가 실제로 포함됐는지 확인한다.
