# 로그 설계

로그는 **사실**의 기록이다. 좋은 로그는 문장을 잘 쓰는 데서가 아니라, 어떤 사실을 언제 어떤 형식으로 남길지 정확히 정하는 데서 시작한다. 이 스킬은 아래 여덟 원칙을 기준으로 두 갈래 일을 한다.

- **감사**: 이미 있는 로그·이벤트·모니터링을 훑어 잘된 점과 문제점을 보고한다. 로그를 추가하는 diff 리뷰도 이 갈래이며, 범위만 diff로 좁힌다.
- **설계**: 새 기능의 이벤트·운영 로그 명세를 쓰거나 리뷰한다.

작업 중인 프로젝트의 로그 지도가 `references/<프로젝트 이름>.md`로 있으면 먼저 읽는다. 이 파일에는 비공개 프로젝트 정보가 들어 있어서 git으로 추적하지 않는다. 원칙의 근거 문서를 인용해야 할 때는 [references/sources.md](references/sources.md)를 본다.

## 여덟 원칙

각 원칙의 **판정** 질문이 감사의 합격 기준이다. 보고에서는 `§번호`로 가리킨다.

**§1 질문과 발생 시점.** 로그마다 무엇을 판단하려는지(제품 분석, 장애 조사, 보안 감사)와 어떤 조건이 성립하면 한 번 기록하는지 정한다. 버튼 클릭, 서버 저장 완료, 후속 처리 완료는 서로 다른 사실이다. 사실을 확정하는 쪽이 그 사실을 기록한다. 결제 완료처럼 중요한 업무 사실은 보통 서버가 확정한다.
판정: 발생 조건을 한 문장으로 말할 수 있고, 이벤트 이름이 그 사실과 일치하는가?

**§2 고정된 이름.** 같은 의미에는 같은 이름, 표기 규칙은 하나다. 사용자·상품·파일 형식처럼 변하는 값은 이름이 아니라 속성에 담는다. 기존 속성명(`document_id`)을 새 기능에서 다른 이름(`file_key`)으로 다시 정의하지 않는다. `started`, `accepted`, `completed`, `failed`의 의미를 팀에서 정해 둔다.
판정: 이벤트 이름과 속성 키가 한 규칙으로 읽히고, 같은 대상이 같은 이름을 쓰는가?

**§3 스키마 계약.** 속성마다 자료형, 필수 여부, 허용 값, 단위를 정한다. `duration_ms`처럼 단위를 이름에 담고, 숫자는 숫자로 보낸다. 필드 생략과 `null`이 각각 무엇을 뜻하는지 정한다. 기존 필드의 의미나 자료형 변경은 스키마 버전 변경으로 다룬다.
판정: 같은 속성의 자료형과 의미가 호출부마다 같고, 값이 없을 때의 의미가 명시적인가?

**§4 추적 가능성.** 서비스와 배포 버전, 요청(`trace_id`)·작업(`job_id`) 식별자, 발생 시각, 실패한 단계, 확인된 오류 코드를 남긴다. 기록할 필드와 인덱싱(라벨, 태그)할 필드는 따로 정한다. 요청 ID나 사용자 ID처럼 값의 종류가 많은 필드를 라벨로 쓰면 **카디널리티**가 폭발한다.
판정: 오류 로그 한 줄로 어느 서비스·버전의 어떤 작업이 어느 단계에서 어떤 코드로 실패했는지 알 수 있고, 클라이언트 오류를 서버 기록과 이을 수 있는가?

**§5 시도와 최종 결과.** 같은 이벤트를 재전송하면 같은 `event_id`를 유지한다. 작업을 다시 시도하면 같은 `job_id` 아래에서 `attempt`를 올린다. 시도 한 번의 실패와 작업 전체의 **최종 실패**를 구분하고, 같은 예외를 여러 층에서 중복 기록하지 않는다.
판정: 중간 재시도 실패가 최종 실패로 집계되지 않고, 최종 실패는 빠짐없이 남는가?

**§6 민감정보는 처음부터 제외.** 비밀번호, 토큰, 세션 ID, 개인정보, 사용자 입력 원문, 요청·응답 본문 전체는 남기지 않는다. 원문 대신 목적에 필요한 분류나 파생값(`has_memo`, `name_length`)을 남긴다. **허용 목록**에 있는 필드만 기록하고, 자유 문자열은 길이를 제한하고 줄바꿈을 막아 로그 위조를 차단한다. 접근 권한과 보존 기간도 명세에 넣는다.
판정: 오류 설명 문자열을 포함해 어떤 경로로도 원문이 밖으로 나가지 않는다고 코드로 보장되는가?

**§7 레벨과 알림은 따로.** `DEBUG`는 진단 세부, `INFO`는 정상 상태 변화, `WARN`은 복구했거나 계속 진행하지만 확인이 필요한 상황, `ERROR`는 그 작업을 완료하지 못한 상황이다. 오프라인이나 사용자 취소처럼 예상된 결과는 `ERROR`가 아니다. `ERROR` 한 줄이 곧 이슈나 호출이 되지는 않는다. 알림은 오류율, 반복 횟수, 사용자 영향으로 따로 설계한다.
판정: 레벨이 위 정의대로 쓰이고, 이슈·알림 생성이 레벨과 별개로 정해지는가?

**§8 강제와 도착.** 규칙을 문서뿐 아니라 타입, 테스트, 수집 도구로 강제한다. 필수 필드 누락, 금지 키, 경로별 발생 횟수(성공·실패·재시도), 전송 실패 시 앱 영향, 수집 유실 감지를 테스트한다. 로그가 운영 환경에서 실제로 목적지에 **도착**하는지도 확인한다.
판정: 규칙을 어기는 코드가 테스트나 컴파일에서 걸리고, 운영 빌드의 로그가 목적지에 도착하는가?

## 감사

범위는 사용자가 지정한 저장소, 디렉터리, diff다. 앱과 서버가 다른 저장소에 있으면 둘 다 본다. 사용자가 하나만 지정했으면 그것만 본다.

1~2단계의 출구 표와 이름 목록은 판정을 위한 작업 메모다. 답변에는 판정에 쓰인 증거만 옮긴다. diff 리뷰는 1~2단계를 건너뛰고, diff에 보이는 출구와 이름으로 3단계부터 한다.

1. **출구 목록.** 코드에서 바깥으로 나가는 로그 출구를 모두 찾는다. OS 로그(`os_log`, `Logger`, `print`), 크래시·모니터링 SDK, 분석 SDK, 서버 콘솔 로그, 이벤트를 저장하는 DB 테이블이 출구다. 출구마다 감싸는 래퍼, 호출부 수, 환경별 활성 조건(개발 빌드에서 꺼지는지)을 적는다. 앱 확장, 위젯, 백그라운드 작업, 크론, 웹훅도 실행 대상에 넣는다.
   완료: 모든 실행 대상이 출구 표에 있고, 출구가 없는 대상은 "없음"으로 적혀 있다.
2. **이름과 키 목록.** 분석 이벤트 이름과 로그 속성 키를 grep으로 전부 뽑아 표기 규칙별로 묶는다. 자료형이 어긋난 키, 운영 이벤트에 섞인 개발용 속성, 같은 대상에 다른 이름을 쓰는 경우를 표시한다.
   완료: 이벤트 이름 전체 목록이 규칙별로 분류되어 있다.
3. **원칙별 판정.** §1~§8 각각에 증거를 찾아 판정한다. 다음은 놓치기 쉬운 곳이다.
   - **조용한 경로**: 로그가 있는 것처럼 보이지만 운영에서 목적지에 도착하지 않는 곳. 기본값이 no-op인 로거를 호출부에서 직접 만드는 코드, `catch` 뒤에 아무것도 남기지 않는 곳, `try?`로 버리는 실패, 개발 빌드에서만 켜지는 출구가 여기에 속한다.
   - 래퍼의 기본 이슈 정책과 호출부를 대조해, `ERROR` 호출 중 몇 개가 이슈를 만드는지 센다.
   - 서버 오류 코드와 호출한 서버 함수 이름이 클라이언트 로그 속성으로 구조화되는지, 메시지 문자열에 묻히는지 본다.
   - 오류 설명 문자열(`String(describing: error)`, `error.message`)이나 공개 로그 설정(`privacy: .public`)으로 원문이 새는 경로를 찾는다.
   - 기한이나 법적 의무가 있는 백그라운드 작업(계정 삭제, 결제, 알림 발송)의 실패, 재시도, 기한 초과가 로그나 알림으로 드러나는지, DB 상태로만 남는지 본다.
   - 로거 정책과 이벤트 규칙을 검사하는 테스트가 있는지 본다.
   - 모니터링 설정 자체를 본다. 크래시 심볼 업로드(dSYM, source map), 샘플링 비율과 사용량 한도, 로그 보존 기간, 분석·모니터링 키가 운영 빌드에 실제로 들어가는지가 대상이다. CI 스크립트와 빌드 설정에 있다.
   완료: 여덟 원칙 모두에 판정(잘됨, 문제, 해당 없음)이 있고, 판정마다 `파일:줄` 근거가 있다.
4. **사실과 추정.** 코드로 확인한 것과 대시보드(Sentry, Amplitude, 서버 로그 콘솔)를 봐야 알 수 있는 것을 나눈다. 대시보드를 보지 못했으면 실제 영향에 대한 주장에 `[추정]`을 붙인다.

### 감사 답변

답변은 보고서가 아니라 채팅 답이다. 사용자가 다음 행동을 정하는 데 필요한 것만 결론 → 근거 → 다음 행동 순서로 담는다. 본문은 아래 네 부분뿐이다. 제목, 점검 대상과 기준일 머리말, 출구 표나 이벤트 목록 같은 부록, 전제와 가정 절은 사용자가 요청할 때만 덧붙인다.

문제는 다음 순서로 우선순위를 매기고, 많아야 6개까지 쓴다. 나머지는 "그 밖에" 한 줄로 묶는다.

1. 운영에서 아무 신호도 남지 않는 조용한 경로, 민감정보 유출
2. 집계와 추적을 깨는 이름, 오류 코드, 상관관계 문제
3. 노이즈와 표기 일관성

이벤트 이름 변경처럼 과거 데이터와의 연속성을 끊는 수정은 코드만 보고 정하지 않는다. 대시보드의 과거 데이터를 확인한 뒤 사용자가 정하도록 남긴다.

```markdown
결론 2~3문장: 기본 틀 평가, 가장 큰 문제 2~3개.

## 잘 되어 있는 것
3~5개, 항목당 한 줄 (§번호, 파일:줄)

## 문제점
**N. 한 줄 요약 (§번호)**
- 증거: 파일:줄, 무엇이 어떻게 되어 있는지 (1~2줄)
- 영향: 무엇을 판단하거나 추적할 수 없게 되는지 (1줄)

## 다음 단계
작고 독립적인 수정부터 3~5개. 항목마다 무엇을 바꾸고 몇 번 문제를 닫는지.

## 확인하지 못한 것
결론을 바꿀 수 있는 것만 1~3줄.
```

완료: 답변이 위 네 부분으로만 되어 있고, 문제마다 `§번호`와 `파일:줄`이 있다.

## 설계

1. **질문.** 이 로그로 무엇을 판단할지, 누가 쓸지(제품 분석, 운영, 보안)를 한 문장으로 적는다. 답할 질문이 없으면 로그를 추가하지 않는 것도 결론이다.
2. **사실과 발생 지점.** 기록할 사실, 한 번 기록하는 정확한 조건, 그 사실을 확정하는 주체(클라이언트 상호작용인지, 서버 확정인지)를 정한다. 핵심 업무 하나의 시작, 성공, 최종 실패를 한 묶음으로 설계한다.
3. **기존 어휘 재사용.** 저장소의 기존 이벤트 이름과 속성 키를 검색해, 같은 개념은 같은 이름으로 쓴다.
   완료: 새 속성마다 기존 키 검색 결과와 재사용 여부(신규라면 이유)가 적혀 있다.
4. **명세.** 아래 템플릿을 채운다.
5. **민감정보와 카디널리티.** 속성마다 원문인지 파생값인지, 인덱스·태그로 쓸지 본문 필드로 둘지 정한다.
6. **검증 계획.** 경로별 발생 횟수(성공, 실패, 재시도), 필수 필드, 금지 키를 확인하는 테스트를 적는다. 기록용 테스트 대역(recording client)이 있으면 그것으로 단위 테스트를 쓴다.

### 명세 템플릿

| 항목 | 내용 |
|---|---|
| 이름 | |
| 종류 | 분석 이벤트, 운영 로그, 감사 로그 중 하나 |
| 목적 | 이 로그가 답할 질문 |
| 발생 조건 | 어떤 조건이 성립하면 한 번 기록하는가 |
| 발생 주체 | 클라이언트 또는 서버, 그렇게 정한 이유 |
| 레벨과 알림 | 운영 로그라면 레벨, 이슈·알림 생성 조건 |
| 속성 | 속성 표: 이름, 자료형, 필수 여부, 허용 값, 단위, 설명 |
| 식별자 | `event_id`, `job_id`, `attempt`, `trace_id` 중 필요한 것 |
| 민감정보 | 제외한 원문과 대신 남기는 파생값 |
| 스키마 버전 | |
| 검증 | 테스트 목록 |

운영 로그 예시(문서 처리 작업의 최종 실패):

```json
{
  "event_name": "document.parse.failed",
  "schema_version": 1,
  "event_id": "evt_example_03",
  "timestamp": "2026-10-30T03:15:21.123Z",
  "severity": "ERROR",
  "service_name": "parser-worker",
  "job_id": "job_example",
  "attempt": 3,
  "final": true,
  "duration_ms": 30000,
  "error_code": "PARSER_TIMEOUT",
  "retry_scheduled": false
}
```

이 한 줄로 어느 작업의 몇 번째 시도가 실패했는지, 최종 결과인지, 얼마나 걸렸는지, 재시도가 예정되어 있는지 알 수 있다.
